## Problem Statement

BrowserLens is a local-first macOS menu bar app for fast recall across Safari and Chrome history and bookmarks. It should feel like an Apple-native utility: friendly, quiet, keyboard-first, and fast enough to become daily muscle memory.

The app must never send browsing activity to the cloud. It should run in the background, regularly index browser activity, deduplicate URLs, and expose a Spotlight-style search window with filters for browser, item type, and date.

## What Makes This Cool

The cool version is not just "search browser history." Raycast and browser-native history already cover that basic job.

BrowserLens should be a private browsing memory map. The useful moment is: "I know I saw this. Find it instantly and show me the thread." It should help recover not only the page, but the surrounding context: related visits, bookmarks, domains, and time windows that explain how the user got there.

The product wins by being narrower than Rewind-style capture tools and deeper than Raycast browser extensions:

- Narrower than Rewind because it does not record screen, audio, page contents, or the whole desktop.
- Deeper than Raycast because it treats browser activity as deduped, grouped, recall-oriented memory.
- More trusted because "local only" is visible in the product behavior, not just a marketing claim.

## Constraints

- macOS first.
- Safari and Chrome are the primary supported browsers.
- Local-only storage and indexing.
- No analytics, no cloud sync, no remote AI calls in v1.
- Menu bar launch and global hotkey.
- Search must feel instant on realistic personal browsing history.
- Background indexing should avoid heavy CPU, battery, or disk usage.
- Browser database reads must handle locked SQLite files safely by copying to a temporary location before reading.
- The UI should feel native, friendly, and Apple-style rather than like a developer admin tool.

## Premises

1. BrowserLens is a personal Mac utility first, not a SaaS or social product.
2. Its core promise is privacy-first activity recall across Safari and Chrome history/bookmarks, with all indexing and search local.
3. v1 should optimize for speed, deduped URL search, source/type/date filters, and a menu bar launch flow.
4. Session/rabbit-hole grouping belongs in the first architecture because it is the main differentiator from Raycast.
5. Natural-language recall should be deferred until the deterministic local index and grouping model feel excellent.
6. The product should compete less with Raycast as a launcher and more with the browser-memory gap inside Raycast: richer recall UI, grouping, and privacy clarity.

## Cross-Model Perspective

Codex recommended framing BrowserLens as a "local browsing memory map," not just history search. The strongest point was that the magic is reconstructing context: "what was I doing when I found this?"

Codex recommended a native macOS prototype using Swift + SwiftUI, AppKit `NSStatusItem`, a global hotkey package, SQLite FTS5 through GRDB, and a local Application Support database. It suggested skipping natural-language recall, embeddings, page content indexing, screenshots, sync, and Rewind-style recording until the core fast search loop is excellent.

## Approaches Considered

### Approach A: Minimal Native v1

Build the native menu bar app with Safari/Chrome import, URL dedupe, SQLite FTS search, filters, and a keyboard-first Spotlight window. Session grouping and natural-language recall come later.

Effort: M
Risk: Low

Pros:

- Fastest path to a daily-use app.
- Proves the hardest habit loop: hotkey, type, find, open.
- Keeps the first implementation smaller and easier to verify.

Cons:

- Less differentiated from Raycast at first glance.
- Delays the memory-map idea that makes BrowserLens feel special.
- May require later data-model changes if grouping is bolted on after the fact.

Reuses:

- macOS menu bar app patterns.
- SQLite FTS5 for local search.
- Existing browser history/bookmark file formats and ingestion ideas from Raycast extensions.

### Approach B: Memory Map Architecture

Build the same native fast-search base, but design the index around visits, canonical URLs, sources, and sessions from day one. The v1 UI still stays simple, but results can show grouped context such as "same rabbit hole," nearby visits, repeat visits, and bookmark status.

Effort: L
Risk: Medium

Pros:

- Directly supports the product thesis: privacy-first activity lens with better recall UI.
- Avoids painting the data model into a search-only corner.
- Gives BrowserLens a clear reason to exist beyond Raycast extension search.

Cons:

- More complexity before the search loop is proven.
- Session grouping can become fuzzy and distracting if the heuristics are weak.
- Requires more careful performance work because grouping queries can slow search.

Reuses:

- Native macOS app shell and SQLite FTS5 from Approach A.
- Browser import logic from Safari and Chrome local stores.
- A local sessionization model based on time windows, domains, canonical URLs, and browser source.

### Approach C: Raycast-First Prototype

Start as a Raycast extension or reuse extension patterns to validate ingestion and search before building the native app.

Effort: S
Risk: Medium

Pros:

- Fastest way to validate browser ingestion and simple search behavior.
- Raycast already solves launcher UI and keyboard flow.
- Useful for learning browser file formats before committing to native UI.

Cons:

- Delays the Apple-style standalone utility the user actually wants.
- Privacy trust is partly inherited from Raycast rather than owned by BrowserLens.
- Harder to express session memory and richer recall UI inside launcher constraints.

Reuses:

- Raycast extension ecosystem patterns.
- Existing browser history and bookmarks command structure.

## Recommended Approach

Chosen approach: Approach B, Memory Map Architecture.

BrowserLens should still ship a focused v1, but the storage model should be built for browser memory rather than plain search. The first app should include fast search, filters, dedupe, and a basic "context" treatment for each result: source browsers, history/bookmark status, last seen, visit count, nearby visits, and a simple session group label.

The right v1 promise:

"Hit a hotkey, type a few letters, find the page instantly, and see the trail around it without sending anything off your Mac."

## Open Questions

- Should v1 support only Chrome Default profile, or all Chrome profiles found under `~/Library/Application Support/Google/Chrome/`?
- Should Safari Reading List be treated as bookmarks in v1?
- What is the preferred global hotkey?
- Should BrowserLens open results in the original source browser or the current default browser?
- How aggressive should URL canonicalization be for query params beyond common tracking parameters?
- How visible should privacy controls be in the first-run UI versus a settings screen?

## Success Criteria

- Opens from the menu bar or global hotkey in under 150 ms after initial launch.
- Returns local results interactively while typing for a personal history database.
- Indexes Safari and Chrome history/bookmarks without corrupting or locking browser files.
- Deduplicates the same canonical URL across Safari, Chrome, history, and bookmarks.
- Filters by browser, history/bookmark type, and date.
- Opens the selected result with Enter and copies URL with Cmd+C.
- Shows enough context to explain why a result matched: title, URL, domain, browser, type, last seen, visit count, and session context.
- Runs background indexing without noticeable battery or CPU impact.
- Makes the privacy model obvious: local database path, no network calls, no analytics, and clear controls to pause or clear indexing.

## Distribution Plan

Initial distribution should be a local Xcode-built `.app` for personal use.

Once the app is worth keeping installed, distribute through GitHub Releases:

- Build signed macOS app artifact.
- Package as `.dmg` or `.zip`.
- Publish release notes and checksum.
- Add a minimal auto-update path later using Sparkle only if the app becomes shared beyond personal use.

CI/CD can start simple:

- GitHub Actions builds and tests the Swift package/app.
- A manual release workflow creates the distributable artifact.
- Notarization can be added when sharing with other users becomes a goal.

## Dependencies

- SwiftUI for the main UI.
- AppKit `NSStatusItem` for menu bar integration.
- AppKit or a lightweight package for a global hotkey.
- SQLite FTS5 through GRDB or direct SQLite APIs.
- macOS file access permissions for browser data locations.
- Browser-specific importers:
  - Safari history and bookmarks/Reading List.
  - Chrome history and bookmarks, starting with Default profile.
- URL canonicalization utility.
- Background scheduling through app timers or macOS background-friendly scheduling.
